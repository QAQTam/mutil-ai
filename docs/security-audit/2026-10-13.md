## F1 — P1：默认跨 origin 重定向会转发自定义认证头和 POST 正文

**位置**：`src/adapter/anthropic.rs:61,144`；`src/adapter/endpoint.rs:78,373`。其他 adapter 同样使用 `reqwest::Client::new()`。

**原因**：SDK 没有配置 redirect policy。锁定版本的 reqwest 在跨 origin 跳转时会移除标准 Authorization/Cookie 等头，但不移除 `x-api-key` 或任意自定义认证头；307/308 保留 POST 正文。`HeaderValue::set_sensitive(true)` 只能帮助日志脱敏，不能代替重定向控制。

**复现**：`cross_origin_307_forwards_api_key_and_private_body`。本地 `localhost:A` 返回指向 `127.0.0.1:B/capture` 的 307，B 实际收到：

```text
POST /capture
x-api-key: audit-fake-secret
... PRIVATE_PROMPT ...
```

**前提与影响**：配置的 provider/gateway 返回跨 origin redirect，目的地不在调用方授权范围内。导致该目的地收到 API Key、prompt、历史或工具数据。即使 Bearer 被 reqwest 移除，307/308 下正文仍可能离开原来的信任域；若重定向到内部服务，还会越过上层仅对初始 URL 做的目的地检查。这不是经典 TOCTOU，而是检查范围没有覆盖后续网络跳转。

**建议**：统一通过受控 ClientBuilder 创建 client；默认禁止跳转，或严格限制同 origin（scheme/host/effective port）。确需跨 origin 时逐跳重新批准目标并重建认证，不沿用原 body/凭据。HTTPS 降级也应拒绝；开发用 HTTP 应显式允许。

**依据**：本地 `reqwest-0.13.5/src/redirect.rs` 的 `remove_sensitive_headers` 和已运行的 HTTP PoC。上游实现可参见 [reqwest redirect 源码](https://github.com/seanmonstar/reqwest/blob/master/src/redirect.rs)。本报告结论以锁定版本的本地源码和复现为准，不依赖 master 的版本假设。

## F2 — P1：错误/配置日志会输出 API Key

**位置**：`src/adapter/gemini.rs:156`；`src/error.rs:133,265`；`src/headers.rs:164,381`。

**原因**：Gemini 把 key 放进 URL query；`Error::Http` 直接保留并格式化 reqwest error，其 URL 未脱敏。`RequestOptions` / `TransportConfig` Debug 还直接输出 HeaderMap，普通 `.header("x-api-key", ...)` 不会将 HeaderValue 标成 sensitive。

**复现**：

- `gemini_transport_error_debug_contains_query_api_key`：模拟服务器不返回 HTTP 响应，`error.to_string()` 和 `format!("{error:?}")` 都包含 `AUDIT_FAKE_QUERY_SECRET`。
- `sensitive_custom_headers_are_visible_in_options_debug`：RequestOptions Debug 包含 `AUDIT_FAKE_HEADER_SECRET`。

**前提与影响**：应用按 SDK 的“错误可安全记录”契约记录错误或调试配置；日志系统、告警或终端的读者获得 provider 凭据。通用 `AuthStyle::QueryKey` 也受 URL 错误输出影响。

**建议**：进入 SDK 错误边界时对 URL 做统一脱敏，优先 `without_url()`，或仅保留脱敏后的 origin/path。所有内建与自定义认证头应标记 sensitive；Debug 使用显式安全摘要，不直接输出 query/header/context。敏感值只能通过明确的诊断接口获取。

reqwest 本身明确提示包含 query API key 的错误 URL 要用 `without_url` 移除，见 [reqwest Error 文档与源码](https://docs.rs/reqwest/latest/src/reqwest/error.rs.html)。

## F3 — P2：流内 provider error 原文绕过日志脱敏

**位置**：`src/adapter/openai_chat.rs:1011`；`src/adapter/openai_responses.rs:824`；`src/adapter/anthropic.rs:912`；`src/adapter/gemini.rs:806`；`src/error.rs:148,273`。

**原因**：四个 mapper 把上游 error JSON / event 直接 `to_string()` 装入 `ProviderStream(String)`；该 variant 的 Display 和 Debug 原样输出。HTTP `Api` variant 的 raw body 已做脱敏，但同等内容只要通过 SSE 返回就逃过了这层保护。

**复现**：`provider_stream_error_display_and_debug_leak_raw_message`，上游发送包含 `PRIVATE_PROMPT_ECHO` 的 error，Display/Debug 都可见该内容。

**前提与影响**：provider/gateway 错误中回显输入、工具参数或其他敏感信息；应用常规记录错误即泄露上下文。非受信任端点还可向日志注入任意多行文本。

**建议**：将流错误与 HTTP 错误统一为结构化、log-safe 输出；原文只通过显式 raw accessor 暴露。分类器可以内部读取 raw，但不能把原文当用户可记录的 error message。

## F4 — P2：工具配对不满足一对一/ID 完整性

**位置**：`src/normalize.rs:568,635,640,671`。

**复现与原因**：

1. `duplicate_tool_result_is_accepted_for_already_fulfilled_call`：按 ID 查找没有判断 `!fulfilled`，已完成调用的第二个结果仍被接受。
2. `explicit_wrong_call_id_falls_back_to_name_but_keeps_wrong_id`：结果显式带 `foreign` ID，待配对调用 ID 是 `expected`；查 ID 失败后按名字匹配，标记 `expected` fulfilled，却保留结果的 `foreign` ID。缺失结果也不再被合成。
3. `generated_tool_call_id_collides_with_existing_id`：已有 `call_1`，第二个无 ID 调用仍被赋成 `call_1`；生成器不避让已有 ID，同一轮出现歧义。

**前提与影响**：并发工具调度、历史导入、插件回传等产生重复、延迟、错 ID 结果，或调用方接收非受信任历史。SDK 会接受重放/错配结果、串到错误调用，或生成 provider 拒绝的历史。可能污染后续模型决策；本 SDK 不执行工具，因此本审计没有证明直接越权工具执行。

**建议**：同一匹配范围内保持 ID 唯一；预先收集已有 ID，生成 ID 时避让。显式 ID 必须精确匹配且调用未完成；ID 不存在时执行 orphan policy，禁止按名称兜底。名称兜底仅限真正缺失 ID 的结果；结果名称与匹配调用冲突时拒绝或显式报告。对重复调用 ID 和重复结果给出明确策略。

## F5 — P2：普通 SSE 连接上的合法重复事件被静默去重

**位置**：`src/stream.rs:336,342`；`src/sse.rs` 的 last-event-id 继承逻辑本身是正确的。

**原因**：`process_sse` 只要看到 ID 就按 `(id, data)` 去重，即使没有启用 reconnect、当前仍是第一次连接。SSE ID 会继承，不是每个事件必然唯一的序号；缓存 key 还忽略了 `event` 类型。

**复现**：`inherited_sse_id_drops_legitimate_repeated_deltas_without_reconnect`。仅首事件设置 `id: cursor`，接着两个 `content: "ha"` delta；应得到 `haha`，实际返回 `ha`，并正常发出 Done，没有提示数据损坏。

**影响**：重复文本或工具参数片段被删，工具 JSON/最终值可能被改变。属于数据完整性问题，不是传统竞态。SSE 允许后续事件继承上次 ID，见 [WHATWG SSE 标准](https://html.spec.whatwg.org/multipage/server-sent-events.html#parsing-an-event-stream)。

**建议**：普通连接不去重；只在明确约定的重连 replay 窗口内去重。需要 server 保证 resume/序号语义，不能把继承 ID 当唯一标识。区分 event 类型和重复事件次数，不要简单永久维护 `(id, data)` 集合。

## F6 — P2：默认 HeaderPolicy 不保护非 Bearer 认证头

**位置**：`src/headers.rs:317,534,598`；`src/adapter/anthropic.rs:144`；`src/adapter/endpoint.rs:373,379`。

**原因**：默认 protected 集合只包含标准 Authorization/Content-Type/Content-Length/Host/Accept；不包含 Anthropic 的 `x-api-key`，也不会根据 EndpointSpec 的 XApiKey/Custom auth header 扩展保护。

**复现**：`request_options_can_replace_anthropic_auth_header_without_opt_in`。adapter 用 `trusted-key` 初始化，普通 `RequestOptions.header("x-api-key", "untrusted-key")` 无需 allow_override，服务器最终收到 `untrusted-key`。

**前提与影响**：下游允许请求级 header 扩展，而凭据选择应由可信 transport 管理。非受信任请求可覆盖所用 provider 账户/计费身份。若 header 全由同一可信应用构造，风险较低，但这仍不符合 SDK 声称的受保护认证边界。

**建议**：保护当前 adapter 的实际认证 header，包括自定义 header；仍然保留显式 allow_override 和可信 HeaderInjector 通道。QueryKey 的实际认证参数也应被动态列入 reserved-query 检查；目前 EndpointAdapter 的该检查只按 Gemini 的 `key`/`alt` 固定名字生成，属于需要同时补齐的静态审查项。

## F7 — P2：单行/单事件限制没有约束整体响应内存与累积 CPU

**位置**：`src/adapter/mod.rs:636`；`src/adapter/openai_chat.rs:1013,1107,1142`；`src/stream.rs:342,346`。其余 mapper 也保留 `chunks` 并累积输出。

**原因**：

- 普通 JSON 和错误正文使用 `response.text()` 整体读入，没有 decoded body 大小上限；启用 gzip 时应限制解压后的数据，而不是只检查 Content-Length。
- SSE parser 有 64 KiB line / 1 MiB event 上限，但 mapper 的文本、推理、工具参数和 raw chunks 可以一直增长，没有 request-wide byte/event/part budget。
- 去重虽限制 4096 个条目，但 HashSet 与 VecDeque 分别持有完整 `(id,data)` clone，按数量限制不等于按字节限制。接近 1 MiB 的合法事件可使这部分数据理论上接近 8 GiB，尚未计入 raw JSON 与输出；这只是源码上界估算，没有运行 OOM 实验。
- OpenAI Chat 每次工具参数 delta 都 clone 完整 `arguments_so_far`，长参数流的总复制量可随分片数出现二次增长。该 CPU 放大属于静态确认，未做性能基准。

**复现**：`streaming_accumulates_more_than_parser_event_limit`：40 个合法约 60 KiB delta 被接受，最终保存 `2,457,600` 字节文本及 40 份 raw chunks。该实验确认跨事件累积没有被 parser 限制；无限增长与内存耗尽风险由控制流分析得出，不是已运行的 OOM。

**前提与影响**：上游持续输出合法小事件、超大 JSON 或压缩正文；多个 session 下可导致内存/CPU 耗尽。流式输出不等于常量内存，因为 SDK 还构造完整 response。

**建议**：提供 decoded response byte budget、事件/工具/part 数量限制、单工具参数与 reasoning/text 限制；raw 收集应可关闭或有界。去重缓存按字节预算并避免重复存储全文；ToolCallProgress 使用显式 opt-in、节流或其他受限策略。超限返回结构化错误并停止读取。

## F8 — P2：所谓总 timeout 不覆盖整个逻辑请求，reconnect 等待也不受服务端延迟上限约束

**位置**：`src/headers.rs:138,565`；`src/adapter/mod.rs:655,673,720`；`src/adapter/openai_chat.rs:192`；`src/stream.rs:435`。

**原因**：`options.timeout` 只传给每次 RequestBuilder，计时在异步 HeaderInjector 完成之后开始；重试 sleep 不在 timer 内，每次 attempt/reconnect 又重新获得完整 timeout。`schedule_reconnect` 直接使用 SSE retry 和 error delay hint，没有类似 RetryPolicy.max_retry_after 的限制，等待期间还关闭 idle deadline。

**复现**：

- `total_timeout_does_not_cover_header_injector`：SDK timeout = 10 ms，injector sleep 100 ms；外部 50 ms watchdog 已超时，SDK 仍未返回。探针在 injector 完成前取消 future，未发送远程请求。
- `total_timeout_does_not_cover_retry_after_sleep`：timeout = 100 ms，server Retry-After = 150 ms，之后请求仍成功，整体超过 150 ms。
- `reconnect_retry_hint_bypasses_http_retry_after_cap`：max_retry_after = 1 s，但 SSE `retry: 86400000` 后实际安排了 24 小时 reconnect 等待。探针只检查 Retrying event，立即 drop，未等待一天。

**前提与影响**：动态 token provider 挂起或上游引导长等待；网关 worker/session 超过调用方预算而保持存活，破坏资源与取消策略。不是必须设置不合理的本地 timeout 才会发生。

**建议**：逻辑请求入口生成一个 monotonic absolute deadline，覆盖 injector、attempt、body read、retry sleep，以及返回流后的读/重连过程。每个阶段使用剩余预算，不重置总时钟；为 SSE reconnect 增加独立 max_delay 或复用明确的 server-delay 上限。CancellationToken 继续作为独立主动取消路径。

## TOCTOU 与未计为漏洞的检查结果

- `src/` 未发现生产文件 I/O、文件存在性检查、外部进程启动或 `unsafe` 代码，缺少经典路径/符号链接 TOCTOU 的直接攻击面。
- 请求经 transform 后再 capability gating、normalization 和序列化；`&ChatRequest` / `&RequestOptions` 在安全 Rust 中不能由另一线程直接并发修改，body/query 被保存用于重试，因此没有找到“校验的请求与发送的请求被其他线程替换”的具体路径。
- CancellationToken 通过共享 AtomicBool 加 watch 通知；watch 保存状态、receiver 存活，未发现常见 Notify 先检查后注册导致的 lost wakeup。
- HeaderInjector 是明确的可信扩展；它更换 token 是既定能力，不能仅凭其跨 await 读取外部状态就认定 SDK 存在 TOCTOU。下游若能让其在重试间切换 tenant/主体，应自行维持逻辑请求身份绑定；本次没有审计具体 injector 实现。
- 初始 base URL/EndpointSpec 允许调用方显式配置，这是 API 能力本身。如果下游把这些字段直接交给租户，需在下游实施 SSRF 网络准入；不能将“允许自定义 endpoint”单独定性为 SDK 漏洞。F1 是已具体复现的后续跳转越界。
- 最小 agent 示例只演示本地注册工具，不是带审批的生产 runtime。本审计没有将缺少 runtime 权限系统错误地计为 SDK 漏洞。
- 本机没有安装 `cargo-audit`，因此**未完成依赖 RustSec 数据库审计**，也没有声称依赖不存在已知漏洞。本次为源码/行为审计，不是完整供应链、模糊测试或下游授权系统评估。

## 复现方式

在仓库根目录 PowerShell 执行。Manifest 放进已忽略的 `target/`，不会改变主 crate 的 Cargo.lock 或正常测试入口：

```powershell
$auditHarness = Join-Path (Get-Location) 'target/security-audit-poc'
New-Item -ItemType Directory -Force -Path $auditHarness | Out-Null
Copy-Item -LiteralPath 'docs/security-audit/Cargo.toml.template' -Destination (Join-Path $auditHarness 'Cargo.toml')
Copy-Item -LiteralPath 'Cargo.lock' -Destination (Join-Path $auditHarness 'Cargo.lock')
cargo test --manifest-path target/security-audit-poc/Cargo.toml --target-dir target --offline --test poc -- --test-threads=1
```

`--offline` 需要本机已缓存依赖。探针源码见 [poc.rs](poc.rs)。网络 probe 使用本地假服务器；所有 secret 字符串均为假值。

## 推荐修复顺序

1. F1 重定向信任域、F2 API Key 日志脱敏。
2. F3 统一流错误脱敏、F6 动态保护实际认证字段。

4. F7 总字节/事件预算、F8 逻辑请求绝对 deadline 与 reconnect delay 上限。

每一类修复后把对应 PoC 改成“不会泄露/不会接受错配/不会丢 delta/会按预算失败”的回归测试，再运行相关测试及完整 all-features 检查。
